## On-device Lua

MCU Lua is a device-local API rather than a network SDK. Its complete data
shapes, event payloads, constraints, and runnable examples are in the
[On-Device Lua API](/docs/lua).

Non-blocking snapshots:

- `Mighty.info()`
- `Mighty.state()` and the compact state helpers
- `Mighty.pose()`
- `Mighty.imu()`
- `Mighty.tracker()` / `Mighty.tracker_status()`
- `Mighty.recording_status()`
- `Mighty.loop_closure_status()`
- `Mighty.camera_sync_status()`
- `Mighty.next_event()`

Typed controls:

- `Mighty.start_vio([timeout_ms])`
- `Mighty.stop_vio([timeout_ms])`
- `Mighty.start_recording([directory], [timeout_ms])`
- `Mighty.start_imu_recording([directory], [timeout_ms])`
- `Mighty.stop_recording([timeout_ms])`
- `Mighty.set_loop_closure_enabled(enabled, [timeout_ms])`
- `Mighty.reset_vio_pose(pose, [timeout_ms])`
- `Mighty.start_tracker(rect, [timeout_ms])`
- `Mighty.stop_tracker([timeout_ms])`
- `Mighty.set_camera_sync_enabled(enabled, [timeout_ms])`

Bounded generic controls:

- `Mighty.command(name, [argument], [timeout_ms])`
- `Mighty.command_async(name, [argument])`
- `Mighty.command_result([request_id])`

The generic command functions use a fixed whitelist; they are not an
unrestricted protocol or shell bridge. Depth and large vision/configuration
payloads are not exposed to MCU Lua.

## Tracker telemetry and LOST behavior

The JavaScript, Python, and C++ network SDKs deliver tracker telemetry through
the VIZ subscription. State values are stable across the three SDKs:

| Code | State | Meaning |
| ---: | --- | --- |
| `0` | `stopped` | No tracker session is active. |
| `1` | `waiting` | Start was accepted; the tracker is waiting for its first camera result. |
| `2` | `tracking` | A current target rectangle is available. |
| `3` | `error` | Tracking stopped because initialization, inference, or frame validation failed. |
| `4` | `lost` | Inference continues, but no candidate is trusted as the target. |
| `255` | `unknown` | The state is unavailable or not recognized. |

Current Mighty NanoTrack firmware uses this default state machine on both host
ONNX and device RKNN paths:

1. Initialization extracts ORB features from a centered ellipse inside the
   selected box. If at least 12 are available, ORB becomes the identity gate.
2. While TRACKING, NanoTrack runs on every frame. Two consecutive low raw
   scores enter LOST without running ORB.
3. Every 10 high-score proposals, ORB checks the box against the latest trusted
   appearance plus a bounded bank. A verified sample is retained; a high Nano
   score alone never updates the bank. Low-texture samples cast no identity
   vote. Two failed periodic identity checks enter LOST and freeze the last
   accepted box; unchecked frames do not clear that failure streak. Tracking
   samples use a 300-feature, four-level extractor; the 2,000-feature,
   eight-level full-frame extractor is reserved for LOST.
4. LOST runs image-wide ORB detection with up to 2,000 features and matches all
   retained views using Hamming distance, nearest/second ratio, mutual-nearest,
   and affine-RANSAC checks. Two geometrically consistent detections are
   required to reacquire.
5. On reacquisition, Mighty refreshes NanoTrack's model template at the found
   rectangle, retains the new ORB view, resumes TRACKING, and sets `reacquired`
   for that result only.
6. If the initial box is too textureless for ORB, or ORB is disabled, the
   previous NanoTrack-score and expanding-local-search policy remains the
   fallback.

ORB is best suited to textured, mostly rigid targets. Deformable, textureless,
or strongly viewpoint-changing targets may remain LOST and may require a
learned verifier.

Tracker VIZ fields have these semantics:

- `confidence` is normally NanoTrack's raw positive-class score during
  TRACKING. On a periodic ORB check it is the ORB identity quality, or zero for
  a definite identity mismatch. During LOST it is nonzero only when the
  full-frame search has a geometrically valid candidate. None of these forms
  is a calibrated probability that identity is correct. A UI percentage is
  `round(confidence * 100)`.
- `searchScale` / `search_scale` is the crop scale used for that result. It is
  `1.0` in ORB-gated mode because LOST search is image-wide. It grows only in
  the NanoTrack-only fallback mode.
- `reacquired` is a one-result pulse, not a persistent state.
- `detections` contains the current `Tracker` rectangle while TRACKING. It is
  empty for WAITING, LOST, ERROR, and STOPPED. Applications may retain the last
  TRACKING rectangle solely to visualize the last known location.
- LOST updates continue on every processed inference result, carrying the
  latest confidence and search scale. The device-local `tracker_lost` lifecycle
  event is emitted only when entering LOST.
- Older subtype-4 producers may omit structured tracker telemetry. In that
  case JavaScript/Python expose `tracker: null` and an `unknown` convenience
  state; C++ leaves `VizFrame::tracker` empty.

The thresholds and search behavior are firmware-side settings, not SDK calls.
Their environment overrides are `MIGHTY_TRACKER_LOST_CONFIDENCE`,
`MIGHTY_TRACKER_REACQUIRE_CONFIDENCE`, `MIGHTY_TRACKER_LOST_FRAMES`,
`MIGHTY_TRACKER_REACQUIRE_FRAMES`, `MIGHTY_TRACKER_SEARCH_EXPAND_STEP`,
`MIGHTY_TRACKER_MAX_SEARCH_SCALE`, and
`MIGHTY_TRACKER_LOST_WINDOW_INFLUENCE`. ORB re-detection is controlled by
`MIGHTY_TRACKER_ORB_REACQUIRE`, `MIGHTY_TRACKER_ORB_MAX_FEATURES`,
`MIGHTY_TRACKER_ORB_FAST_THRESHOLD`, `MIGHTY_TRACKER_ORB_SCAN_INTERVAL`,
`MIGHTY_TRACKER_ORB_TEMPLATE_INTERVAL`,
`MIGHTY_TRACKER_ORB_TRACKING_FAILURES`, `MIGHTY_TRACKER_ORB_MAX_TEMPLATES`,
`MIGHTY_TRACKER_ORB_MIN_TEMPLATE_FEATURES`,
`MIGHTY_TRACKER_ORB_MIN_MATCHES`, `MIGHTY_TRACKER_ORB_MIN_INLIERS`,
`MIGHTY_TRACKER_ORB_CONFIRM_DETECTIONS`, `MIGHTY_TRACKER_ORB_RATIO_TEST`,
`MIGHTY_TRACKER_ORB_MAX_HAMMING`,
`MIGHTY_TRACKER_ORB_MIN_INLIER_RATIO`, `MIGHTY_TRACKER_ORB_RANSAC_PX`,
`MIGHTY_TRACKER_ORB_MIN_INLIER_SPAN`, `MIGHTY_TRACKER_ORB_MIN_SCALE`,
`MIGHTY_TRACKER_ORB_MAX_SCALE`, and
`MIGHTY_TRACKER_ORB_MIN_VISIBLE_FRACTION`.

### JavaScript calibration

`getCalibration()` fetches the active `calib` config and normalizes it. This
means a replay bag's calibration override is resolved by Mighty before the SDK
returns the object. `parseCalibrationYaml(yaml)` exposes the same normalizer for
calibration text already held by the application. Both Kalibr `cam0`/`cam1`
YAML and Mighty's flat OpenCV FileStorage YAML are accepted.

```ts
type RigidTransform3d = {
  matrix: number[]; // 16 row-major values
  valid: boolean;
};

type CameraCalibration = {
  id: string;                         // "cam0", "cam1", ...
  cameraModel: "pinhole" | "double_sphere" | "unknown";
  distortionModel: "none" | "radtan" | "equidistant" | "unknown";
  intrinsics: { fx: number; fy: number; cx: number; cy: number };
  projectionParameters: number[];     // double-sphere: [xi, alpha]
  distortionCoefficients: number[];
  resolution: { width: number; height: number };
  topic: string;
  timeShiftCameraImuS: number;
  cameraFromImu: RigidTransform3d;
  bodyFromCamera: RigidTransform3d;
  valid: boolean;                     // valid canonical intrinsics
};

type Calibration = {
  sourceFormat: "kalibr" | "opencv";
  cameras: CameraCalibration[];
};
```

Transform names are literal `targetFromSource` mappings. For example,
`cameraFromImu` satisfies `p_camera = T_camera_imu * p_imu`, and
`bodyFromCamera` satisfies `p_body = T_body_camera * p_camera`. Matrices are
row-major homogeneous transforms. `body` is the public `base_link` FLU frame
at the IMU origin; camera coordinates are optical right/down/forward. A
transform has `valid: false` when its source field was absent or invalid.

- `onPose(cb)`
- `onImu(cb)`
- `onVioState(cb)`
- `onViz(cb)`
- `onPointCloud(cb)`
- `onStatus(cb)`
- `onLuaLog(cb)`

`onDepth`:

Most applications only need `timestampNs`, `width`, `height`,
`depthAtMeters(...)`, and optionally `rectifyImageToDepth(...)`. The remaining
fields below are advanced camera-alignment metadata; they describe the public
pixel geometry, not the depth model or its implementation.

```ts
type MetricDepthFrame = {
  kind: "depth";
  timestampNs: bigint;       // same capture timestamp as the source image
  width: number;
  height: number;
  depthMm: Uint16Array;      // row-major; invalidValue is not a measurement
  invalidValue: number;      // normally 0
  depthScaleM: number;       // normally 0.001
  depthConvention: number;   // DEPTH_CONVENTION.Z_DEPTH
  depthIntrinsics: [number, number, number, number];  // fx, fy, cx, cy
  sourceWidth: number;
  sourceHeight: number;
  sourceIntrinsics: [number, number, number, number]; // fx, fy, cx, cy
  cameraModel: number;
  distortionModel: number;
  distortion: [number, number, number, number];
  sourceChannel: string;     // normally "cam0"
  frameId: string;           // normally "cam0_rectified"
};
```

`onRgbd` pairs image and depth events by the exact capture timestamp and the
canonical camera channel (`preview` and `left` alias to `cam0`):

```js
const unsubscribe = client.onRgbd(({ image, depth }) => {
  if (image.kind !== "raw") return;

  // The source image is distorted; put it on the same rectified pixel grid as
  // depth before using corresponding pixels.
  const rectified = rectifyImageToDepth(image, depth);
  const centerX = Math.floor(depth.width / 2);
  const centerY = Math.floor(depth.height / 2);
  const centerDepthM = depthAtMeters(depth, centerX, centerY);
  console.log(depth.timestampNs, centerDepthM, rectified.rgba);
});
```

`rectifyImageToDepth(image, depth, { requireMatchingTimestamp = true })`
returns `{ width, height, rgba, timestampNs, frameId }`. It supports raw
`GRAY8`, RGB/BGR(A), and YUV luma input. It throws on mismatched nonzero
timestamps by default.

`colorizeDepth(depth, { nearM = 0, farM = 10 })` returns presentation-only
Turbo RGBA. It does not modify metric samples. `depthAtMeters` returns `null`
for an invalid or out-of-bounds sample.

`onPose`:

```ts
type PoseEvent = {
  poseType: "body" | "camera" | "other";
  poseTypeRaw: number;
  poseFlags: number;
  frameId: "odom";
  childFrameId: "base_link";
  positionM: [number, number, number];
  orientationXyzw?: [number, number, number, number];
  confidence: number;                   // [0, 1]
  isKeyframe: boolean;
  linearVelocityBodyMps?: [number, number, number];
  angularVelocityBodyRps?: [number, number, number];
  linearAccelerationBodyMps2?: [number, number, number];
  angularAccelerationBodyRps2?: [number, number, number];
  timestampNs?: bigint;
};
```

`confidence` is an ordinal pose-usability score, not a probability of absolute
accuracy:

- `confidence >= 0.5`: the current synchronized full 6DoF pose is available.
- `0.2 <= confidence < 0.5`: use orientation only; translation is deliberately
  held and is not a current 6DoF measurement.
- `confidence < 0.2`: do not consume the full 6DoF pose. Inspect the VIO state;
  during `RECOVERING`, keep the device still.

Within the full-6DoF band, larger values indicate stronger current visual
support. The score cannot detect global drift that is not observable from the
current sensor measurements, so consumers should also monitor `onVioState`.

### Python calibration

`client.get_calibration()` fetches and normalizes the active device or replay
calibration. `parse_calibration_yaml(yaml)` performs the same normalization on
an existing string. The returned `value` uses this stable snake-case schema:

```python
{
  "source_format": "kalibr" | "opencv",
  "cameras": [{
    "id": str,
    "camera_model": "pinhole" | "double_sphere" | "unknown",
    "distortion_model": "none" | "radtan" | "equidistant" | "unknown",
    "intrinsics": {"fx": float, "fy": float, "cx": float, "cy": float},
    "projection_parameters": list[float],
    "distortion_coefficients": list[float],
    "resolution": {"width": int, "height": int},
    "topic": str,
    "time_shift_camera_imu_s": float,
    "camera_from_imu": {"matrix": list[float], "valid": bool},
    "body_from_camera": {"matrix": list[float], "valid": bool},
    "valid": bool,
  }],
}
```

Each matrix has 16 row-major values and follows `target_from_source` naming.
`body_from_camera` maps optical right/down/forward camera points into the
public FLU `base_link` frame at the IMU origin. The parser accepts Kalibr
multi-camera YAML and flat OpenCV FileStorage YAML.

### C++ metric-depth helpers

The helper path intentionally hides wire encoding and camera-model branching
from normal users. Access `DepthFrame` calibration fields directly only when
implementing custom alignment or 3D reconstruction.

```cpp
#include "mighty_sdk.h"

using namespace mighty_protocol::sdk;

RgbdSynchronizer synchronizer(
    [](const RawImageFrame& image, const mighty_protocol::DepthFrame& depth) {
      RectifiedRgbaFrame rectified;
      if (!rectify_image_to_depth(image, depth, &rectified)) return;

      const uint32_t x = depth.width / 2;
      const uint32_t y = depth.height / 2;
      const std::optional<float> z_m = depth_at_meters(depth, x, y);
    });

auto image_sub = client.on_image([&](const ImageFrame& frame) {
  synchronizer.push_image(frame.left);
  if (frame.right) synchronizer.push_image(*frame.right);
});
auto depth_sub = client.on_depth([&](const mighty_protocol::DepthFrame& depth) {
  synchronizer.push_depth(depth);
});
```

`RgbdSynchronizer` matches the canonical source channel and exact nanosecond
timestamp. `rectify_image_to_depth` returns `false` for unsupported raw formats,
invalid geometry, or mismatched nonzero timestamps. `depth_at_meters` returns
`std::nullopt` for invalid or out-of-bounds samples.
