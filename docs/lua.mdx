---
title: On-Device Lua API
description: Write bounded Lua programs that react to VIO, IMU, loop closure, tracking, recording, and device state.
---

Mighty runs a sandboxed Lua 5.4 program on the RV1106 MCU. Lua stays alive
independently of the ARM vision process, so it is a good place for LEDs, button
policy, serial protocols, small state machines, and reactions to public device
events.

Edit `/build/userdata/mcu/user.lua` from the device `/code` page.
`Save + Reload` installs the program and starts a fresh Lua state. `RESET`
restores the shipped default program. It does not factory-reset the device.

Depth images, camera images, keyframes, descriptors, point clouds, and full
configuration payloads are intentionally not exposed to MCU Lua.

## Program shape

```lua
function setup()
  -- Called once after a successful load.
end

function loop(dt_ms)
  -- Called repeatedly. Keep this short and non-blocking.
end
```

Globals persist until the next reload. `dt_ms` is elapsed device time since the
previous call and is clamped after long pauses.

The runtime provides selected base, table, string, and math functions. It does
not provide `io`, `os`, `package`, `debug`, `dofile`, `loadfile`, unrestricted
`load`, or filesystem access. The Lua heap is fixed at 256 KiB.

## Snapshot and command model

Snapshot calls such as `Mighty.pose()`, `Mighty.imu()`, and `Mighty.state()` are
non-blocking reads. They never run vision work on the MCU. ARM publishes small,
fixed-size snapshots through shared memory:

- Pose is refreshed with public pose output.
- IMU is refreshed from the latest received sample.
- Runtime, tracker, identity, and configuration summaries refresh at low rate.
- `arm_connected` becomes false when ARM publication is more than two seconds
  old, rather than leaving stale state marked as connected.

All nanosecond timestamps and 64-bit counters are Lua strings. This preserves
their exact values on the 32-bit MCU. Convert them only if your application can
tolerate loss of integer precision.

Control calls normally block until ARM acknowledges the command or the timeout
expires. The asynchronous command API is available when `loop()` must never
wait.

## Time

```lua
millis()          -- monotonic milliseconds
Mighty.time_ns() -- monotonic nanoseconds as a decimal string
```

ARM periodically aligns the MCU clock. The MCU extrapolates between alignment
updates, so `millis()` continues to advance even during a short ARM stall.

## Runtime state

The compact helpers are:

```lua
Mighty.arm_connected()
Mighty.recording()
Mighty.preview_mode()
Mighty.initializing()
Mighty.vio_state() -- returns name, numeric code
```

`Mighty.vio_state()` names are `off`, `initializing`, `tracking`, `degraded`,
`lost`, `low_light`, and `recovering`.

`Mighty.state()` returns the full low-rate status:

```lua
local s = Mighty.state()

-- Connection and app mode
s.arm_connected
s.arm_age_ms
s.recording
s.recording_mode       -- "none", "full", or "imu_only"
s.preview_mode
s.initializing
s.vio_state
s.vio_state_code
s.led_state
s.led_state_code

-- VIO health
s.timestamp_ns
s.age_ms
s.fps_current
s.fps_average
s.imu_hz_current
s.imu_hz_average
s.pose_confidence
s.tracking_rate
s.translation_confidence
s.translation_observability
s.feature_count
s.loop_closures
s.flags

-- Initialization and degradation diagnosis
s.init_reason
s.init_reason_code
s.static_init_reason
s.static_init_reason_code
s.dynamic_init_reason
s.dynamic_init_reason_code
s.degraded_reason_flags
s.degraded_reasons      -- array of stable snake_case names

-- Other bounded summaries
s.memory.total_bytes    -- decimal string
s.memory.used_bytes
s.memory.free_bytes
s.build_version
s.loop_closure.available
s.loop_closure.enabled
s.camera_sync.available
s.camera_sync.enabled
s.camera_sync.applied
s.camera_sync.pending_restart
```

`degraded_reasons` can contain `low_tracking`,
`low_translation_observability`, `low_parallax_pose_hold`,
`stationary_pose_hold`, `high_velocity_low_parallax`, `init_uncertain`,
`static_translation_constrained`, and `rotation_only_3dof`.

Recipe: react only to state changes:

```lua
local previous = nil

function loop()
  local state = Mighty.vio_state()
  if state ~= previous then
    print("vio", state)
    previous = state
  end
end
```

## Public pose

```lua
local pose = Mighty.pose()
```

The snapshot has the same corrected public body pose and kinematics as the
device `POSE` stream:

```lua
{
  valid = true,
  timestamp_ns = "1234567890",
  age_ms = 12.4,
  sequence = 42,
  confidence = 0.92,
  stream = "output",
  pose_type = "body",
  parent_frame = "odom",
  child_frame = "base_link",
  position = { x = 0, y = 0, z = 0 },
  orientation_xyzw = { x = 0, y = 0, z = 0, w = 1 },
  linear_velocity_body = { x = 0, y = 0, z = 0 },
  angular_velocity_body = { x = 0, y = 0, z = 0 },
  linear_acceleration_body = { x = 0, y = 0, z = 0 },
  angular_acceleration_body = { x = 0, y = 0, z = 0 },
}
```

When VIO is unavailable or the ARM snapshot is stale, `valid` is false and the
pose is zero/identity. There is deliberately no `unoptimized_pose()` API:
internal estimator coordinates are not a public stream.

Pose confidence is an ordinal usability signal:

- `>= 0.5`: full 6DoF output is available.
- `>= 0.2` and `< 0.5`: orientation is usable; translation is held.
- `< 0.2`: do not consume full 6DoF output.

Loop closure, AprilTag relocalization, and explicit pose reset rebase the public
output alignment. `Mighty.pose()` and the normal `POSE` stream therefore jump
together on the next publication; the internal estimator state is not mutated.

```lua
function loop()
  local p = Mighty.pose()
  if p.valid and p.confidence >= 0.5 then
    Serial.println(string.format("%.3f,%.3f,%.3f",
      p.position.x, p.position.y, p.position.z))
  end
end
```

## Public event queue

```lua
local event = Mighty.next_event() -- event table, or nil immediately
```

The queue is non-blocking and bounded to eight events. If Lua falls behind,
the oldest events are dropped. A newly loaded script starts with events emitted
after that load.

Public event kinds are:

```lua
-- A newer observation matched an earlier observation and output was corrected.
{
  kind = "loop_closure",
  timestamp_ns = "...",
  matched_timestamp_ns = "...",
  pose = {
    parent_frame = "odom",
    child_frame = "base_link",
    position = { x = 0, y = 0, z = 0 },
    orientation_xyzw = { x = 0, y = 0, z = 0, w = 1 },
  },
}

-- AprilTag relocalization changed public output alignment.
{ kind = "apriltag_relocalize", timestamp_ns = "...", tag_id = 7, pose = {...} }

-- An explicit reset_vio_pose command changed public output alignment.
{ kind = "pose_reset", timestamp_ns = "...", pose = {...} }

-- Public tracker lifecycle/results.
{ kind = "tracker_update", timestamp_ns = "...",
  rect = { x = 10, y = 20, width = 80, height = 60 } }
{ kind = "tracker_lost", timestamp_ns = "0" }
{ kind = "tracker_stopped", timestamp_ns = "0" }
```

Loop-closure events intentionally contain no keyframe IDs, place-recognition
scores, descriptors, graph state, or implementation names.

Drain all currently queued events once per loop:

```lua
function loop()
  while true do
    local event = Mighty.next_event()
    if not event then break end
    if event.kind == "loop_closure" then
      print("loop", event.timestamp_ns, event.matched_timestamp_ns)
    elseif event.kind == "tracker_lost" then
      LED.on()
    end
  end
end
```

## Commands

Blocking commands return `ok, result`:

```lua
{
  id = 12,
  status = "ok",       -- "ok", "error", "timeout", or "busy"
  message = "started", -- success
  error = "...",       -- failure
}
```

Timeouts default to 5000 ms and are clamped to 1–30000 ms.

### VIO

```lua
local ok, result = Mighty.start_vio([timeout_ms])
local ok, result = Mighty.stop_vio([timeout_ms])
```

### Recording

Recording is available in preview mode, not while VIO is active.

```lua
local ok, result = Mighty.start_recording([directory], [timeout_ms])
local ok, result = Mighty.start_imu_recording([directory], [timeout_ms])
local ok, result = Mighty.stop_recording([timeout_ms])

local status = Mighty.recording_status()
-- { active=true, mode="full"|"imu_only"|"none", path="...", arm_connected=true }
```

The default directory is `/mnt/sdcard`. IMU-only recording omits camera frames
but keeps calibration/noise metadata when available.

### Loop closure

```lua
local ok, result = Mighty.set_loop_closure_enabled(true, [timeout_ms])
local status = Mighty.loop_closure_status()
-- { available=true, enabled=true, closures=2 }
```

The toggle controls the same device-side loop-closure worker as the protocol
and SDK command. Enabling it does not run loop closure on the MCU; Lua only
controls and observes the lower-priority ARM/NPU pipeline.

### Public pose reset

```lua
local ok, result = Mighty.reset_vio_pose({
  position = { x = 0, y = 0, z = 0 },
  -- Optional. Omit to keep the current output orientation.
  orientation_xyzw = { x = 0, y = 0, z = 0, w = 1 },
}, [timeout_ms])
```

This rebases public output only. A successful call produces one `pose_reset`
event and subsequent pose snapshots use the new alignment.

### Object tracker

The tracker and VIO are mutually exclusive. Stop VIO before starting tracking.

```lua
local ok, result = Mighty.start_tracker({
  x = 100, y = 80, width = 120, height = 90,
}, [timeout_ms])

local tracker = Mighty.tracker()       -- same as Mighty.tracker_status()
local ok, result = Mighty.stop_tracker([timeout_ms])
```

The tracker snapshot contains `available`, `active`, `state`, `timestamp_ns`,
`rect`, string counters for submitted/processed/dropped frames, `frame_count`,
and an optional `error`. State is `stopped`, `waiting`, `tracking`, or `error`.

### Camera sync

```lua
local ok, result = Mighty.set_camera_sync_enabled(true, [timeout_ms])
local status = Mighty.camera_sync_status()
-- { available=true, enabled=true, applied=true, pending_restart=false }
```

`enabled` is the persisted requested mode. `applied` describes the current
camera datasource. Check `pending_restart` rather than assuming a command took
effect immediately.

### Generic command whitelist

`Mighty.command(name, [argument], [timeout_ms])` is a convenience wrapper, not
an unrestricted ARM command channel. Supported names are:

- `start_vio`
- `stop_vio`
- `start_recording`
- `start_imu_recording`
- `stop_recording`
- `recording_status`
- `loop_closure_status`
- `stop_tracker`
- `tracker_status`
- `camera_sync_status`

Use typed functions for boolean controls, pose payloads, and tracker
rectangles.

### Asynchronous commands

Only one asynchronous command can be outstanding:

```lua
local request_id, error = Mighty.command_async("start_vio")

function loop()
  if request_id then
    local ok, result = Mighty.command_result(request_id)
    if ok ~= nil then
      print(ok and result.message or result.error)
      request_id = nil
    end
  end
end
```

`Mighty.command_result()` returns `nil` while pending. A blocking command returns
`busy` until the asynchronous result has been collected. The asynchronous API
uses the same generic whitelist.

## Button API

```lua
Button.begin()
Button.down()
Button.pressed()       -- one-shot edge
Button.released()      -- one-shot edge
Button.held_ms()
Button.held(ms)        -- one-shot threshold crossing
Button.is_held(ms)     -- continuous level
```

The protected 10-second recovery hold cannot be overridden by Lua. It resets
the USB IP range and camera-sync marker, then reboots.

## Serial API

`Serial` is fixed to UART2 M1. Pin selection is not exposed.

```lua
Serial.begin(115200)
Serial.available()
Serial.read()             -- byte integer or nil
Serial.readBytes(n)       -- binary Lua string
Serial.write("hello")
Serial.writeBytes("\x01\x02")
Serial.print(value)
Serial.println(value)
Serial.flush()
```

## Product-style example

This example uses snapshots and events without blocking the normal loop. A
short press toggles VIO, a 1.2-second hold starts IMU-only recording, and the
LED reflects corrected VIO health.

```lua
local pending = nil
local held_action = false
local last_blink_ms = 0

function setup()
  LED.begin()
  Button.begin()
  Serial.begin(115200)
end

local function request(name)
  local id, err = Mighty.command_async(name)
  if id then pending = id else print("command", err) end
end

function loop()
  local state = Mighty.state()

  if state.recording then
    LED.on()
  elseif state.vio_state == "tracking" then
    LED.on()
  elseif state.vio_state == "degraded" or state.vio_state == "low_light" then
    if millis() - last_blink_ms >= 500 then
      LED.toggle()
      last_blink_ms = millis()
    end
  else
    LED.off()
  end

  if Button.held(1200) and state.preview_mode and not state.recording then
    request("start_imu_recording")
    held_action = true
  elseif Button.released() then
    if state.recording then
      request("stop_recording")
    elseif not held_action then
      request(state.preview_mode and "start_vio" or "stop_vio")
    end
    held_action = false
  end

  if pending then
    local ok, result = Mighty.command_result(pending)
    if ok ~= nil then
      print(ok and result.message or result.error)
      pending = nil
    end
  end

  while true do
    local event = Mighty.next_event()
    if not event then break end
    if event.kind == "loop_closure" then
      Serial.println("loop=" .. event.timestamp_ns .. "," ..
                     event.matched_timestamp_ns)
    end
  end
end
```

## Operational guidance

- Keep `loop()` short; do not busy-wait.
- Store a snapshot in a local variable instead of calling it repeatedly in one
  iteration.
- Use `next_event()` in a drain loop because it is non-blocking.
- Use asynchronous commands for latency-sensitive MCU behavior.
- Check `arm_connected`, snapshot `valid`, and optional capability flags.
- Avoid creating large temporary strings or tables in tight loops.
- Use `/code` logs while developing, then reduce noisy `print()` calls.
